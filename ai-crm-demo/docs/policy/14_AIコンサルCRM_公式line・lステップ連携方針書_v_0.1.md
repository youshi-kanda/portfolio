# AIコンサルCRM 公式LINE・Lステップ連携方針書 v0.1

## 1. 本書の目的

本書は、AIコンサルCRMにおける公式LINE、LINE Messaging API、Lステップ、L Message等のLINE関連ツールとの連携方針を定義するものである。

本サービスは、個人店・小規模店舗が公式LINEを主要な顧客接点として活用しながら、顧客状態・売上課題・地域ニーズを整理し、集客・再来店・顧客フォロー・発信施策をAIに相談しながら実行できるAIコンサル型CRMである。

本書では、以下を明確にする。

- 本サービスと公式LINEの役割分担（Phase 5以降は配信実行まで本サービスが担う）
- 本サービスとLステップ/L Messageの役割分担（Lステップは任意の外部ツール）
- Phase 5でどのLINE機能を実装するか
- LINE Messaging API連携の段階設計
- 同意管理、配信停止、広告表現、料金、監査ログの扱い
- Webhook受信・署名検証の実装方針

---

## 2. 基本方針

### 2.1 公式LINEを主要な顧客接点として扱う

本サービスでは、小規模店舗における主要な顧客接点として公式LINEを前提にする。

理由は以下である。

- 小規模店舗でも導入しやすい
- 顧客との接点として利用されやすい
- 予約、問い合わせ、再来店促進、キャンペーン告知に使いやすい
- 店舗側がすでに運用しているケースが多い
- Lステップ等を使わなくても、一定の配信・個別対応が可能である

ただし、本サービスは公式LINEそのものを置き換えるものではない。

Phase 5以降、本サービスはLINE Messaging APIを通じて配信実行まで担う。公式LINEは顧客との接点・配信チャネルであり、本サービスは「誰に、何を、なぜ、いつ送るか」の判断から配信実行・結果分析まで一貫して提供する。

### 2.2 Lステップは必須ではなく任意ツールとする

LステップやL Messageは、高度なセグメント配信、ステップ配信、シナリオ分岐、リッチメニュー制御などを実行するための有力な外部ツールである。

一方で、個人店・小規模店舗にとっては、以下の課題がある。

- 初期構築が重い
- タグ設計が複雑になりやすい
- シナリオ保守が属人化しやすい
- 運用代行や保守費用が発生しやすい
- 店舗側が理解しきれず、運用が止まりやすい

そのため、本サービスではLステップを必須前提にしない。

公式LINEのみで運用できる店舗には、対象者リスト・文案・実行タイミングを出力する。

高度な自動化が必要な店舗には、Lステップ/L Messageで実行しやすいタグ案・シナリオ案・文案・改善案を出力する。

### 2.3 本サービスの役割

本サービスの役割は、顧客理解からLINE配信実行・結果分析まで一貫して担うことである。

| 領域 | 本サービスの役割 |
|---|---|
| 顧客理解 | 顧客状態、推定ニーズ、阻害要因、次アクションを整理する |
| 施策設計 | 休眠復帰、初回後フォロー、アップセル等の施策を設計する |
| 対象者整理 | 配信・個別フォロー対象者を抽出する（同意・配信停止チェック込み） |
| LINE友だち管理 | Webhookで友だち情報を取得・管理し、顧客と紐付ける |
| 文案生成 | 公式LINE配信文、個別LINE文、シナリオ文を生成する |
| 表現チェック | 業種別の広告表現リスクを検出する |
| 人間承認 | 配信前に必ず承認を通す（承認なしの配信は不可） |
| **LINE配信実行** | **承認済み文案をBroadcast / Multicast / ステップ配信で実行する（Phase 5〜）** |
| 結果分析 | LINE Insights APIで配信結果を取得し、改善に反映する |
| 改善提案 | 施策結果をもとに次回改善案・月次レポートを出す |

|---|---|---|

| 施策結果 | 本サービス | 次回改善に活かすため |
| 承認履歴 | 本サービス | 誤配信・表現リスクを管理するため |

### 3.3 外部LINEツール側に渡す情報

| 情報 | 用途 |
|---|---|
| 対象者リスト | 手動配信、タグ付与、シナリオ投入用 |

| 配信文 | 公式LINE、Lステップ等で送信する文案 |
| シナリオ案 | Lステップ等で構築する流れ |
| 実施タイミング | 配信日時、来店後日数、休眠日数など |
| 注意点 | 配信停止、同意、表現リスク、過剰配信など |

## 4. 利用パターン別の連携方針

## 4.1 パターンA：本サービスでLINE配信まで完結（推奨）

### 4.1.1 位置づけ

Phase 5以降の標準パターン。LINEアカウントを本サービスに接続し、対象者抽出・文案生成・承認・配信実行・結果取得まで本サービス内で完結させる。

### 4.1.2 業務フロー

```text
顧客/予約/売上データを取込
↓
本サービスで顧客状態を判定
↓
AIが今週の施策を提案
↓
対象者リストとLINE文を生成（同意・配信停止自動チェック）
↓
オーナー/店長が承認
↓
本サービスからLINE Broadcast / Multicast配信
↓
LINE Insights APIで配信結果を取得
↓
次回改善案を生成
```

### 4.1.3 本サービスで提供するもの

- LINE Accountとの接続（channel_access_token管理）
- Webhook受信（LINE友だち管理）
- 配信対象者リスト（同意・配信停止チェック込み）
- 除外者リスト・除外理由表示
- AI文案生成・広告表現チェック
- 承認ワークフロー
- LINE Broadcast / Multicast / ステップ配信実行
- LINE Insights API連携による配信結果取得
- 次回改善案・月次レポート生成

### 4.1.4 必須条件

- 配信実行前に承認済みコンテンツであることを確認する
- 配信停止者・同意未取得者を自動除外する
- channel_access_token / channel_secretはDB暗号化保存
- Webhook受信時はHMAC-SHA256署名検証を実施
- 配信・承認・Webhook受信は監査ログに記録する

---

## 4.2 パターンB：Lステップ/L Message利用店舗

### 4.2.1 位置づけ

複雑な自動シナリオ分岐（10ステップ超）・個人別リッチメニュー出し分けなど、Lステップの得意領域を活用したい店舗向けパターン。

本サービスで顧客整理・対象者条件・タグ案・シナリオ案・文案・改善レポートを作り、Lステップ側で高度な配信・自動分岐を実行する。単純な一斉配信は本サービスから直接実行することも可能。

### 4.2.2 業務フロー

```text
顧客/予約/売上/配信結果データを取込
↓
本サービスで顧客状態・ニーズを整理
↓
施策目的に応じて対象者とタグ案を生成
↓
Lステップ用シナリオ案・文案を生成
↓
Lステップ側で構築・配信
↓
結果を本サービスに戻す
↓
改善案を生成
```

### 4.2.3 本サービスで出力するもの

- タグ設計案
- タグ棚卸し案
- シナリオ設計案
- ステップ配信文案
- 分岐条件案
- 対象者条件
- 対象者CSV
- 配信結果入力テンプレート
- 月次改善レポート

### 4.2.4 制約

- Lステップ側のAPI・CSV・外部連携仕様に依存する
- 既存タグが複雑な場合は棚卸しが必要
- 本サービスから直接Lステップを操作する前提にはしない
- 初期はCSV/手入力/設計書出力を中心にする

---

## 4.3 パターンC：代理店・コンサル利用

### 4.3.1 位置づけ

代理店・コンサルが、店舗ごとに公式LINEのみで足りるか、Lステップ等が必要かを判断し、支援方針を決めるために利用する。

```text
店舗診断
↓
公式LINE運用状況を確認
↓
顧客データ・売上データを確認
↓
Lステップ要否診断
↓
支援方針を決定
↓
提案書作成
↓
施策・文案・レポート作成
```

### 4.3.3 出力するもの

- 公式LINE運用診断
- Lステップ要否診断
- 支援方針
- 改善提案書
- 月次レポート
- LINE施策案

## 5. タグ設計方針

### 5.1 基本思想

本サービスは「タグを完全になくす」ことを目指さない。

目指すのは、公式LINEやLステップ側で複雑なタグ設計をしなくても済むように、本サービス側で詳細な顧客理解と施策判断を持ち、外部ツール側には実行に必要な最小限のタグだけを渡すことである。

### 5.2 本サービス側で持つ詳細分類

- 顧客状態
- 推定ニーズ
- 行動阻害要因
- 優先度
- 次アクション
- 判断根拠
- AI信頼度
- 施策履歴
- 反応履歴

### 5.3 外部ツール側に渡す最小タグ

| タグ種別 | 例 | 用途 |
|---|---|---|
| 状態タグ | 初回後フォロー対象、休眠復帰対象、VIP候補 | 配信対象の大枠指定 |
| 施策タグ | 休眠復帰_2026年05月、回数券更新_2026年06月 | 施策単位の配信管理 |
| 注意タグ | 要個別対応、配信停止、クレーム注意 | 誤配信防止 |
| チャネルタグ | LINE配信対象、個別連絡対象 | 実行チャネル識別 |

### 5.4 タグ命名ルール

| 種別 | 命名例 | 方針 |
|---|---|---|
| 状態タグ | 初回後フォロー対象 | 長期利用する状態系 |
| 施策タグ | 休眠復帰_2026年05月 | 施策単位。一時利用前提 |
| 注意タグ | 要個別対応 | 誤配信防止用 |
| チャネルタグ | LINE配信対象 | 実行チャネル管理用 |

### 5.5 タグ棚卸し方針

将来的には、Lステップや公式LINE側のタグ棚卸し支援を行う。

棚卸し観点は以下。

- 使われていないタグ
- 重複しているタグ
- 意味が曖昧なタグ
- 施策終了後も残っている一時タグ
- 顧客状態と施策目的が混在しているタグ
- 個人情報やセンシティブ情報を含むタグ

## 6. 対象者リスト出力方針

### 6.1 対象者リストの目的

対象者リストは、公式LINE、Lステップ、L Message、個別連絡で実行するための実務用リストである。

### 6.2 出力項目

| 項目 | 内容 |
|---|---|
| 顧客ID | 本サービス内の顧客ID |
| 表示名 | LINE名、氏名、ニックネーム等 |
| 顧客状態 | 初回後、休眠、VIP候補など |
| 推定ニーズ | 価格不安、季節悩み、再開きっかけ不足など |
| 推奨アクション | LINE配信、個別連絡、店頭提案など |
| 配信可否 | 同意・配信停止状態 |
| 除外理由 | 配信停止、同意未取得、個別対応中など |
| 外部タグ候補 | 公式LINE/Lステップ用タグ |
| 備考 | 注意点、担当者確認事項 |

### 6.3 CSV出力方針

CSV出力は、初期から重要機能とする。

ただし、以下の制御を行う。

- 権限があるユーザーのみ出力可能
- 出力前に配信停止・同意状態を再確認する
- 代理店ユーザーは個人情報をマスキングできるようにする
- 出力履歴を監査ログに残す
- 出力ファイルには生成日時・店舗名・施策名を含める

### 6.4 除外者リスト

対象者リストには、配信対象だけでなく除外者数と除外理由も表示する。

| 除外理由 | 内容 |
|---|---|
| 配信停止 | is_unsubscribed = true |
| 同意未取得 | contact_line_allowed = false |
| 顧客削除済み | customer.status = deleted |
| 要個別対応 | 一斉配信より個別対応が望ましい |
| 表現リスク | 特定訴求が不適切な可能性 |

## 8. LINE Messaging API連携方針

### 8.1 全体方針

Phase 5以降でLINE Messaging APIによる配信実行を本サービスに実装する。

必須条件：
- 顧客向け配信は人間承認済みのみ実行可能
- 配信対象抽出時は `customer_consents` を必ず参照し、同意未取得・配信停止者を除外
- `LineFriend.is_following = false`（ブロック・フォロー解除済み）を除外
- `channel_access_token` / `channel_secret` はDB暗号化保存
- Webhook署名検証（HMAC-SHA256）を必ず実施
- 配信・承認・Webhook受信は監査ログを記録

### 8.2 Phase 1〜4（完了）：API非依存

| 項目 | 内容 |
|---|---|
| 配信 | 本サービスからは行わない。対象者リスト・配信文を出力し、公式LINE側で手動実行 |
| 出力 | 対象者リスト、配信文、タグ案、実行手順、CSV出力 |
| 結果 | 手入力、CSV取込 |

### 8.3 Phase 5：LINE Harness機能移植・配信CRM化（進行中）

| 項目 | 内容 |
|---|---|
| 目的 | 本サービス内でLINE配信実行まで完結させる |
| 実装対象 | LineAccount管理、Webhook受信、LineFriend管理、Broadcast/Multicast、ステップ配信、自動応答、リッチメニュー、Insights取得 |
| 必須条件 | 承認済み、同意確認済み、配信停止除外、署名検証、監査ログ |
| 参照実装 | LINE Harness OSS（MIT）のアーキテクチャを参考に、Django/React スタックで移植 |

### 8.4 Phase 6以降：高度連携

| 項目 | 内容 |
|---|---|
| 目的 | Audience連携・高度な対象者制御 |
| 実装候補 | Audience連携、メッセージクリック/インプレッションAudience、Narrowcast |
| 注意点 | API制約、料金、審査、外部仕様変更は実装直前に公式ドキュメントで再確認 |

## 9. LINE Audience利用方針

### 9.1 基本方針

LINE Audienceは、将来的な高度配信で利用候補とする。

初期MVPではAudience連携を必須にしない。

### 9.2 利用候補

- userIdアップロードAudience
- メッセージクリックAudience
- メッセージインプレッションAudience

### 9.3 注意点

Messaging APIから作成できるAudienceには制約がある。

チャットタグAudience、友だち追加経路Audience、予約Audience、リッチメニュークリックAudience、リッチメニュー表示Audience、LINE TagのWebトラフィックAudienceなどは、Messaging APIから直接作成できない前提で設計する。

### 9.4 設計への影響

上記制約により、公式LINE側のタグやAudienceを完全に不要にする設計は避ける。

本サービスは、詳細な顧客理解と施策判断を保持し、外部ツール側には必要最小限の実行情報を渡す。

## 10. 配信停止・同意管理

### 10.1 基本方針

顧客へのLINE配信では、配信停止・同意状態を必ず確認する。

### 10.2 配信対象条件

LINE配信対象者は、最低限以下を満たす必要がある。

```text
customer.status = active
AND customer_consents.contact_line_allowed = true
AND customer_consents.is_unsubscribed = false
```

### 10.3 除外条件

| 条件 | 内容 |
|---|---|
| 配信停止 | is_unsubscribed = true |
| LINE連絡同意なし | contact_line_allowed = false |
| 顧客削除済み | customer.status = deleted |
| 要個別対応 | 一斉配信より個別対応が望ましい |
| クレーム注意 | 配信リスクが高い |
| 表現リスク | 特定顧客に不適切な訴求の可能性 |

### 10.4 配信停止反映

将来的にAPI連携する場合、外部ツール側の配信停止・ブロック状態を本サービスへ反映する仕組みが必要になる。

初期は、手入力またはCSV取込で配信停止状態を更新する。

## 11. 料金・通数管理

### 11.1 基本方針

LINE配信は、配信通数や契約プランによって費用が変動する可能性がある。

そのため、本サービスが将来的に半自動・自動配信へ進む場合は、以下を管理する。

- 配信対象者数
- 月間配信予定数
- 配信済み数
- 残り配信可能数
- 配信費用目安
- 配信頻度
- 過剰配信アラート

### 11.2 初期MVPでの扱い

初期MVPでは、公式LINE側の料金計算までは行わない。

ただし、以下の注意表示は行う。

- 配信対象人数
- 月内配信予定回数
- 過剰配信の可能性
- 料金プラン確認の促し

### 12.1 初期方針

初期は自動取得ではなく、手入力またはCSV取込を基本とする。

### 12.2 記録する結果

| 実配信数 | 実際に送信した数 |

| 予約数 | 配信後に発生した予約数 |

### 12.3 改善への反映

結果は、以下に利用する。

- 次回配信文の改善

- キャンペーン条件の見直し
- Lステップ要否診断
- 月次レポート

## 13. Lステップ/L Message連携方針

### 13.1 初期方針

初期は、LステップやL MessageのAPI連携を前提にしない。

理由は以下である。

- サービスごとに仕様が異なる
- 外部連携可否やAPI公開範囲の確認が必要
- タグ・シナリオ・友だち情報の構造がツールごとに異なる
- 店舗ごとの既存構築状態に差がある
- 初期価値は設計案・文案・対象者リストだけでも出せる

### 13.2 初期出力

| 出力 | 内容 |
|---|---|
| タグ設計案 | 最小限のタグ名、用途、対象条件 |
| シナリオ案 | 初回後、休眠、アップセル、回数券更新など |
| 配信文案 | 各ステップで使う文案 |
| 分岐条件案 | 返信あり、予約あり、来店あり、反応なし等 |
| 対象者CSV | タグ付け・配信対象設定の補助 |
| 改善レポート | 配信結果から改善案を生成 |

### 13.3 将来連携候補

- CSVインポート/エクスポート連携
- タグ同期
- 顧客ID・LINE userIdの名寄せ
- 配信結果取込
- シナリオ結果取込
- Webhookや外部API連携

### 13.4 注意点

LステップやL Messageの仕様は、実装前に必ず公式情報・契約プラン・外部連携可否を確認する。

本書では、具体的なAPI仕様を確定仕様として扱わない。

## 14. 承認・監査ログ

### 14.1 承認必須対象

| 対象 | 承認理由 |
|---|---|
| LINE一斉配信文 | 顧客へ直接届くため |
| 個別LINE文 | 顧客対応に影響するため |
| ステップ配信文 | 継続的に顧客へ届くため |
| キャンペーン文 | 価格・条件誤認リスクがあるため |
| Lステップシナリオ案 | 顧客体験全体に影響するため |
| 高リスク表現を含む文案 | 法令・広告表現リスクがあるため |

### 14.2 監査ログ対象

以下は監査ログに残す。

- 対象者リスト生成
- 除外者リスト確認
- CSV出力
- 文案生成
- 広告表現チェック
- 文案修正
- 承認依頼
- 承認
- 差戻し
- コピー/出力
- 配信結果登録
- 配信停止状態変更
