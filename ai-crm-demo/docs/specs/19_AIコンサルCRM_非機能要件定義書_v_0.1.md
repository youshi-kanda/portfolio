# AIコンサルCRM 非機能要件定義書 v0.1

## 1. 本書の目的

本書は、AIコンサルCRMのシステム構築における非機能要件を定義するものである。

AIコンサルCRMは、公式LINEを主要な顧客接点として活用する個人店・小規模店舗向けに、顧客データ・予約/来店データ・売上データ・施策結果・AI相談履歴を扱い、集客・再来店・顧客フォロー・売上改善の次アクションをAIが提案する相談型マーケティングCRMである。

本システムでは、顧客の個人情報、店舗の売上情報、施策結果、AI相談履歴、同意・配信停止情報などを扱うため、機能要件だけでなく、以下の非機能要件を明確にする必要がある。

- セキュリティ
- 個人情報保護
- 権限管理
- 可用性
- 性能
- 拡張性
- 保守性
- 監査性
- バックアップ・復旧
- 外部連携耐性
- AI利用時の安全性
- 運用・監視

---

## 2. 非機能要件の基本方針

### 2.1 基本思想

本サービスは、単なる顧客管理ツールではなく、店舗の売上改善に関わる意思決定支援システムである。

そのため、非機能要件では以下を重視する。

| 方針 | 内容 |
|---|---|
| 個人情報を安全に扱う | 顧客情報、連絡先、接客メモ、LINE関連情報を適切に保護する |
| 店舗データを分離する | 店舗・代理店・支援者間で不要なデータ混在を防ぐ |
| 誤配信を防ぐ | 同意状態、配信停止、承認状態を必ず確認する |
| AI出力を鵜呑みにさせない | 根拠、信頼度、注意点、人間承認を設計に入れる |
| 初期は外部API依存を避ける | LINE、Instagram、Google、予約システムの仕様変更リスクを下げる |
| MVPでも監査ログを残す | CSV取込、出力、AI生成、承認、配信対象抽出を追跡可能にする |
| 将来拡張できる | 代理店利用、外部API連携、業種拡張、地域需要分析に備える |

### 2.2 初期MVPでの優先順位

| 優先度 | 非機能領域 | 理由 |
|---|---|---|
| 最重要 | セキュリティ・権限管理 | 顧客情報・店舗情報を扱うため |
| 最重要 | 同意・配信停止の反映 | 誤配信・トラブル防止のため |
| 最重要 | 監査ログ | 取込・出力・AI提案・承認の追跡が必要なため |
| 高 | データバックアップ | 顧客・売上・施策履歴を失わないため |
| 高 | 性能 | CSV取込・顧客一覧・AI処理の体験に影響するため |
| 高 | AI安全性 | 広告表現・法令・誤提案リスクがあるため |
| 中 | 可用性 | 初期MVPでは過度な冗長化より安定運用を優先 |
| 中 | 拡張性 | 代理店・外部連携・業種拡張に備える |

## 3. 想定システム構成

### 3.1 初期想定構成

初期MVPでは、以下のような構成を想定する。

| 領域 | 初期想定 |
|---|---|
| フロントエンド | React / Next.js / Vue 等 |
| バックエンド | Django REST Framework / FastAPI / Node.js系 |
| DB | PostgreSQL |
| ファイル保存 | S3互換ストレージ、GCS、R2等 |
| AI連携 | OpenAI API、Gemini API等を抽象化して利用 |
| 非同期処理 | Celery、Cloud Tasks、BullMQ等 |
| 認証 | メール/パスワード、JWT、Session、外部Auth候補 |
| デプロイ | Cloud Run、AWS ECS/Fargate、Render等を候補 |
| 監視 | アプリケーションログ、エラートラッキング、死活監視 |

### 3.2 初期方針

初期は、高度な分散構成よりも以下を優先する。

- 実装・運用がシンプルであること
- テナント分離が確実であること
- CSV取込・出力が安定して動くこと
- AI処理が失敗しても業務データが壊れないこと
- 後から外部API連携を追加できること

## 4. セキュリティ要件

### 4.1 認証

| 項目 | 要件 | MVP優先度 |
|---|---|---|
| ログイン | メールアドレス + パスワード、または外部Authで認証する | 必須 |
| パスワード保存 | 平文保存は禁止。安全なハッシュ化を行う | 必須 |
| セッション管理 | セッションまたはJWTの有効期限を設定する | 必須 |
| パスワード再設定 | メール経由で再設定できる | 高 |
| 多要素認証 | 代理店・管理者向けに将来検討 | 将来 |
| ログイン試行制限 | 連続失敗時の制限を行う | 高 |

### 4.2 認可

| 項目 | 要件 | MVP優先度 |
|---|---|---|
| テナント分離 | tenant_id単位でデータアクセスを制御する | 必須 |
| 店舗分離 | store_id単位でデータアクセスを制御する | 必須 |
| ロール制御 | owner / manager / staff / supporter / agency_admin / system_admin を管理する | 必須 |
| 個人情報閲覧制御 | 支援者・代理店は権限に応じてマスキングする | 高 |
| CSV出力制御 | 個人情報を含むCSV出力は権限確認を必須にする | 必須 |
| 承認権限制御 | 外部発信文・配信対象出力は承認権限を確認する | 必須 |

### 4.3 アクセス制御の原則

```text
認証済みである
AND 所属テナントである
AND 対象店舗への権限がある
AND 操作ロールが許可されている
AND 個人情報閲覧・出力権限が必要条件を満たす
```

上記を満たさない場合は、403または404として扱う。

### 4.4 通信暗号化

| 項目 | 要件 |
|---|---|
| HTTPS | 本番環境ではHTTPS必須 |
| API通信 | すべてHTTPS経由 |
| 外部AI API通信 | HTTPS経由 |
| ファイルダウンロード | 署名付きURL等で期限付きアクセスにする |

### 4.5 保存データ保護

| 対象 | 方針 |
|---|---|
| 顧客個人情報 | DB上で権限制御。必要に応じて暗号化を検討 |
| LINE userId | 個人識別に近い情報として厳格に管理 |
| 接客メモ | センシティブ情報を含む可能性があるため権限制御 |
| CSV元ファイル | 一定期間後削除、または暗号化保存 |
| AIログ | 個人情報・店舗機密を含む場合はマスキング・保存期間管理 |

## 5. 個人情報・プライバシー要件

### 5.1 基本方針

顧客個人情報は、店舗内の顧客管理・再来店支援・売上改善の目的に限定して利用する。

横断分析やベンチマークに使う場合は、個人・店舗が特定されない匿名化・集計化データのみを対象とする。

### 5.2 個人情報の分類

| 分類 | 例 | 保護方針 |
|---|---|---|
| 直接識別情報 | 氏名、電話番号、メール | 権限制御・出力制限 |
| 外部識別子 | LINE userId、外部顧客ID | 個人情報に準じて管理 |
| 行動履歴 | 来店日、予約、購入、反応 | 店舗内利用。横断利用は集計化 |
| 接客メモ | 悩み、希望、注意点 | 必要最小限・権限制御 |
| AI相談履歴 | 相談内容、提案内容 | 機密情報を含む前提で管理 |

### 5.3 データ最小化

以下を原則とする。

- 必要以上の個人情報を取得しない
- AIに渡す情報は相談内容に必要な範囲に限定する
- 電話番号・メール・氏名をAI入力に渡す必要がない場合はマスキングする
- 接客メモは全文ではなく要約利用を検討する
- 代理店ユーザーには個人情報を原則マスキングする

### 5.4 配信停止・同意の優先

配信対象抽出では、以下を必ず確認する。

```text
customer.status = active
AND customer_consents.contact_line_allowed = true
AND customer_consents.is_unsubscribed = false
```

メール・SMSの場合は、各チャネルの同意状態を参照する。

## 6. 監査ログ要件

### 6.1 基本方針

本サービスでは、顧客情報・配信対象者・AI生成文・CSV出力など、トラブル時に追跡が必要な操作を監査ログとして記録する。

### 6.2 監査ログ対象操作

| 操作 | MVP必須 | 理由 |
|---|---:|---|
| ログイン | 必須 | 不正アクセス確認 |
| 顧客情報閲覧 | 高 | 個人情報アクセス確認 |
| 顧客情報編集 | 必須 | 誤更新・削除確認 |
| CSVアップロード | 必須 | データ取込履歴確認 |
| CSV取込実行 | 必須 | 取込データの追跡 |
| CSV出力 | 必須 | 個人情報流出防止 |
| 配信対象者CSV出力 | 必須 | 誤配信時の追跡 |
| 除外者CSV出力 | 高 | 同意・停止確認 |
| AI診断実行 | 必須 | AI提案根拠の追跡 |
| AI文案生成 | 必須 | 外部発信文の追跡 |
| 広告表現チェック | 必須 | リスク確認履歴 |
| 承認・差戻し | 必須 | 人間承認の証跡 |
| 配信停止変更 | 必須 | 顧客希望反映の証跡 |
| 権限変更 | 必須 | 管理者操作の追跡 |

### 6.3 監査ログ項目

| 項目 | 内容 |
|---|---|
| id | ログID |
| tenant_id | テナントID |
| store_id | 店舗ID |
| user_id | 操作ユーザー |
| action_type | 操作種別 |
| target_type | 対象種別 |
| target_id | 対象ID |
| before_value | 変更前の値。必要に応じて要約・マスキング |
| after_value | 変更後の値。必要に応じて要約・マスキング |
| ip_address | IPアドレス |
| user_agent | 利用環境 |
| created_at | 操作日時 |

### 6.4 ログ保存期間

| ログ種別 | 保存期間候補 |
|---|---|
| 認証ログ | 1年 |
| 顧客情報操作ログ | 3年 |
| CSV取込・出力ログ | 3年 |
| 承認ログ | 3年 |
| AI生成・チェックログ | 1〜3年 |
| システムエラーログ | 90日〜1年 |

保存期間は、利用規約・プライバシーポリシー・運用コストを踏まえて確定する。

## 7. 可用性要件

### 7.1 稼働目標

| 環境 | 稼働目標 |
|---|---|
| MVP検証環境 | 重大障害時に手動復旧できること |
| β版 | 月間稼働率 99.0% 目安 |
| 正式版 | 月間稼働率 99.5% 以上を目標 |

### 7.2 障害時の基本方針

- AI機能が停止しても、顧客一覧・施策履歴・過去レポートは閲覧できるようにする
- CSV取込失敗時に、DBの一部だけが不整合にならないようにする
- 外部AI APIの障害時は、再実行・保留・手動対応に切り替える
- 外部LINE/SNS/APIの障害が本サービス全体停止につながらないようにする

### 7.3 外部依存障害への対応

| 外部依存 | 障害時対応 |
|---|---|
| AI API | AI生成を一時停止し、過去結果・手入力運用を可能にする |
| ファイルストレージ | CSVアップロード/出力を一時停止し、画面閲覧は継続 |
| LINE API | 初期は直接依存しない。将来連携時は手動配信へ退避 |
| Google/Instagram API | 初期は直接依存しない。将来連携時は手入力へ退避 |

## 9. データ整合性要件

### 9.1 基本方針

顧客・予約・売上・施策・AI提案は、店舗IDを中心に整合性を保つ。

### 9.2 必須整合性

| 対象 | 要件 |
|---|---|
| 顧客 | store_idに必ず紐づく |
| 予約/来店 | 顧客または仮顧客に紐づく |
| 売上 | 顧客または仮顧客に紐づく |
| 施策 | store_idに必ず紐づく |
| 施策対象者 | campaign_id と customer_id に紐づく |
| AI提案 | store_id、必要に応じて customer_id / campaign_id に紐づく |
| 同意状態 | customer_id と store_id に紐づく |

### 9.3 CSV取込時の整合性

| ケース | 方針 |
|---|---|
| 顧客未登録の予約 | 仮顧客作成または警告表示 |
| 顧客未登録の売上 | 仮顧客作成または警告表示 |
| メニュー未登録 | warningとして取り込み、後で紐付け可能にする |
| 重複顧客 | 自動統合せず、候補表示に留める |
| 配信停止情報 | 既存値より優先して反映する |

## 10. バックアップ・復旧要件

### 10.1 バックアップ対象

| 対象 | 方針 |
|---|---|
| PostgreSQL DB | 定期バックアップ必須 |
| アップロードCSV | 保存期間中はバックアップ対象 |
| 出力CSV | 短期保存。必要に応じて再生成可能にする |
| AI生成結果 | DB保存分をバックアップ対象 |
| 監査ログ | バックアップ対象 |
| 設定ファイル | バージョン管理対象 |

### 10.2 バックアップ頻度

| 環境 | 頻度候補 |
|---|---|
| MVP検証 | 1日1回 |
| β版 | 1日1回 + 重要操作前バックアップ検討 |
| 正式版 | 1日1回以上、必要に応じてポイントインタイムリカバリ |

### 10.3 復旧目標

| 指標 | MVP目標 | 正式版目標 |
|---|---|---|
| RPO | 24時間以内 | 数時間以内を検討 |
| RTO | 1営業日以内 | 数時間以内を検討 |

### 10.4 復旧時の注意

- 顧客同意・配信停止情報は最優先で復旧する
- 施策対象者リストは誤復旧に注意する
- CSV取込途中のジョブは再実行可能にする
- 復旧後は監査ログとデータ整合性を確認する

## 13. AI安全性要件

### 13.1 AI利用の基本方針

AIは、意思決定支援・施策設計支援・文案生成支援として扱う。

以下はAIに担わせない。

- 売上向上の保証
- 法的判断の代替
- 医療判断の代替
- 完全自動配信の最終判断
- 顧客への重要連絡の完全自動化

### 13.2 AI出力に必要な項目

AI提案には以下を含める。

| 項目 | 内容 |
|---|---|
| 提案内容 | 何をするか |
| 対象 | 誰に向けた施策か |
| 目的 | 何を改善するためか |
| 根拠 | どのデータから判断したか |
| 信頼度 | 高・中・低 |
| 注意点 | 表現、法令、同意、データ不足など |
| 実行手順 | 具体的な進め方 |
| 人間確認要否 | 承認が必要か |

### 13.3 AI入力データ制御

| データ | 方針 |
|---|---|
| 氏名 | 原則マスキング可能にする |
| 電話番号 | AI入力には原則不要 |
| メール | AI入力には原則不要 |
| LINE userId | AI入力には原則不要 |
| 接客メモ | 必要に応じて要約・マスキング |
| 売上・来店履歴 | 分析に必要な範囲で利用 |
| 同意状態 | 配信・分析判断に必ず利用 |

### 13.4 広告表現チェック

顧客向け・外部向け文案には、以下を実施する。

- リスクキーワード検出
- 業種別注意表現チェック
- AIによる文脈チェック
- リスクレベル表示
- 修正案提示
- 人間承認
- チェック結果ログ保存

## 14. 運用・監視要件

### 14.1 監視対象

| 対象 | 内容 |
|---|---|
| アプリ稼働 | 死活監視 |
| APIエラー | 5xx / 4xx の増加 |
| DB | 接続数、遅延、容量 |
| CSV取込 | 失敗件数、処理時間 |
| AI API | 失敗率、応答時間、利用量 |
| ファイルストレージ | アップロード失敗、容量 |
| バックアップ | 成功/失敗 |
| ログ容量 | 保存量・肥大化 |

### 14.2 アラート候補

| 条件 | 対応 |
|---|---|
| アプリ停止 | 管理者通知 |
| DB接続失敗 | 管理者通知 |
| CSV取込失敗が連続 | 管理者通知・ユーザー表示 |
| AI API失敗が連続 | AI機能一時停止・管理者通知 |
| CSV出力異常 | 管理者通知 |
| 権限エラー急増 | 不正アクセス疑いとして確認 |

### 14.3 運用管理

- 管理者画面でテナント・店舗・ユーザー状態を確認できる
- 取込ジョブ状態を確認できる
- AI処理キュー状態を確認できる
- エラー内容をユーザー向け・開発者向けに分ける
- 個人情報を含むログを不用意に出さない

## 15. エラーハンドリング要件

### 15.1 基本方針

エラーは、利用者が次に何をすればよいか分かる形で表示する。

### 15.2 エラー分類

| 種別 | 例 | 表示方針 |
|---|---|---|
| 入力エラー | 必須項目不足、日付不正 | 修正箇所を明示 |
| 権限エラー | 閲覧・出力不可 | 権限不足を表示 |
| CSVエラー | 文字コード、項目不一致 | 行番号・項目・修正案を表示 |
| AIエラー | 生成失敗、タイムアウト | 再実行・後で試す案内 |
| 外部APIエラー | LINE/Google等の失敗 | 外部サービス側の問題として表示 |
| システムエラー | 予期せぬ障害 | 問い合わせ用IDを表示 |

### 15.3 エラーレスポンス形式

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります。",
    "details": [
      {
        "field": "sale_date",
        "message": "日付として読み取れません。"
      }
    ]
  },
  "meta": {
    "request_id": "req_xxx"
  }
}
```

## 17. 法令・規約対応要件

### 17.1 基本方針

本サービスは、法令適合性を保証するものではなく、リスクを下げる支援機能を提供する。

最終判断は、店舗運営者、代理店・コンサル、必要に応じて専門家が行う。

### 17.2 対応すべき領域

| 個人情報保護法 | 利用目的、同意、削除・開示対応、委託先管理 |
| 景品表示法 | 優良誤認・有利誤認を避ける |
| ステルスマーケティング規制 | PR表記漏れを防ぐ |
| 薬機法 | 美容・健康表現に注意 |
| 医療広告・関連規制 | 整体・接骨・鍼灸領域で注意 |
| LINE規約 | Messaging API、配信、Audience等の仕様確認 |
| Meta規約 | Instagram API利用時の審査・権限確認 |
| Google規約 | GBP API利用時の権限・割当確認 |

### 17.3 実装前確認

外部API・法令・広告表現に関わる機能は、実装前に公式情報を再確認する。

## 19. MVPで必須の非機能要件

### 19.1 必須

| 項目 | 内容 |
|---|---|
| テナント・店舗単位の権限制御 | 他店舗データを見られないようにする |
| 顧客個人情報の閲覧・出力制御 | 代理店・スタッフ権限に対応する |
| 同意・配信停止の対象者除外 | 誤配信防止のため必須 |
| CSV取込エラー表示 | 店舗担当者が修正可能にする |
| CSV出力監査ログ | 個人情報流出リスクに備える |
| AI提案の根拠・信頼度・注意点表示 | AIの過信を防ぐ |
| 外部発信文の人間承認 | 広告表現・誤配信対策 |
| バックアップ | 顧客・売上・施策データ保護 |
| エラーレスポンス共通化 | 開発・運用しやすくする |

### 19.2 後回し可能

| 項目 | 理由 |
|---|---|
| 多要素認証 | 正式版・代理店展開前に検討 |
| 高度な冗長構成 | MVPではコスト過多 |
| リアルタイム外部API監視 | 初期は外部API非依存 |
| DWH/BI基盤 | 横断分析フェーズで対応 |
| 自動スケーリング最適化 | 利用量増加後でよい |
| SSO | 代理店・法人利用拡大後でよい |
