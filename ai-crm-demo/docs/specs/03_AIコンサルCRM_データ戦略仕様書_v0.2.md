## 1. 本仕様書の目的

本仕様書は、AIコンサルCRMにおいて収集・蓄積・分析・活用するデータの方針を定義するものである。

本サービスの中核価値は、公式LINEを主要チャネルとする小規模店舗向けに、顧客データ・来店/売上データ・LINE友だちデータを統合し、AIが施策提案・配信文生成・対象者抽出・承認・LINE配信実行・結果分析まで一貫して支援することである。Phase 1〜4では判断支援・施策設計・代理店管理ツールとして完成し、Phase 5以降でLINE配信実行まで完結するAI搭載型LINE CRMとなる。

そのため、本仕様書では以下を明確にする。

- どのデータを取得・蓄積するか
- 顧客セグメントやタグをどこで管理するか
- 公式LINEやLステップにはどの情報を渡すか
- Lステップなしでも運用できるデータ構造にするにはどうするか
- 代理店・コンサルが複数店舗を支援する場合に必要なデータは何か
- 将来的な業種別・地域別データ活用をどう設計するか
- 個人情報・店舗情報・施策データの二次利用をどう制御するか

## 1.1 最新情報・法令・外部API仕様の検証方針

本仕様書は、実装前に必ず最新の一次情報に基づいて確認・更新する。

特に以下は、仕様変更や法令改正の影響を受けやすいため、設計時点・実装前・リリース前に再確認する。

| 確認対象 | 確認内容 | 主な確認元 |
|---|---|---|
| 個人情報保護法 | 利用目的、第三者提供、匿名加工情報、仮名加工情報、開示・削除対応 | 個人情報保護委員会 |
| LINE連携 | Messaging API、配信通数、課金、Webhook、Audience、userId取得条件 | LINE Developers、LINE for Business |
| Lステップ/L Message連携 | API、CSV、タグ登録、シナリオ連携、外部連携可否 | 各サービス公式情報 |
| Instagram連携 | 投稿、インサイト、アカウント種別、API権限、審査 | Meta for Developers |
| Googleビジネスプロフィール | パフォーマンス、口コミ、投稿、API利用条件、割当 | Google for Developers |
| 広告・表現規制 | 景品表示法、ステルスマーケティング、薬機法、医療広告、業種別表現 | 消費者庁、厚生労働省、関連ガイドライン |
| AI利用 | 生成AIの利用範囲、説明責任、禁止表現、人間承認 | 各AI API規約、社内運用規定 |

### 1.1.1 設計上の基本姿勢

- 最新情報が未確認の外部仕様は、確定仕様として扱わない
- 初期段階では外部API依存を避け、CSV・Googleスプレッドシート・手入力を基本とする
- LINE、Instagram、Googleなどの外部連携は、実装直前に公式ドキュメントで再確認する
- 法令・規約に関わる機能は、仕様書上で「要法務確認」と明記する
- AI提案は意思決定支援であり、成果保証や法的判断の代替として扱わない
- 顧客への外部発信は、原則として人間承認を必須とする

### 1.1.2 情報鮮度の管理

仕様書・設計書には、以下の管理項目を持たせる。

| 項目 | 内容 |
|---|---|
| 最終確認日 | 公式情報を確認した日付 |
| 確認元URL | 参照した公式ドキュメント |
| 影響範囲 | 料金、API、法令、UI、データ設計など |
| 更新要否 | 仕様変更が必要か |
| 担当者 | 確認・更新した担当者 |

## 2. データ戦略の基本思想

### 2.1 基本方針

AIコンサルCRMでは、店舗運営に関するデータを以下の目的で活用する。

1. 店舗ごとの売上改善
2. 顧客ニーズの可視化
3. 休眠・離脱リスクの早期発見
4. 公式LINEを活用した再来店・顧客フォロー施策の提案
5. Instagram・Googleビジネスプロフィール等の発信改善
6. Lステップが必要かどうかの判断支援
7. Lステップ導入済み店舗のタグ設計・シナリオ設計支援
8. 代理店・コンサルの診断・提案・月次レポート支援
9. 業種別テンプレートの高度化
10. 将来的な地域需要分析・新規サービス開発

### 2.2 重要な考え方

本システムにおけるデータは、単なる管理情報ではなく、以下の4層で価値を持つ。

| 階層 | 内容 | 主な利用目的 |
|---|---|---|
| 店舗内データ | 個別店舗の顧客、予約、売上、施策、発信データ | 店舗ごとの改善提案 |
| 実行チャネルデータ | 公式LINE、Lステップ、Instagram、Google等の実行・反応データ | 配信・発信・施策改善 |
| 業種別集計データ | 同業種における施策傾向、顧客状態、反応傾向 | 業種別テンプレート改善、ベンチマーク |
| 地域別集計データ | エリアごとのニーズ、競合傾向、季節需要 | エリア需要分析、新規サービス開発 |

### 2.3 データ活用の前提

データ活用は、以下の前提を守る。

- 個人情報を必要以上に取得しない
- 顧客・店舗に対して利用目的を明示する
- 店舗ごとの営業情報を競合店舗へ直接流用しない
- 個人や店舗が特定される形で横断分析しない
- AI提案には可能な限り根拠・信頼度・注意点を示す
- 重要な外部発信や顧客配信は人間承認を前提にする
- 法令、プラットフォーム規約、業種別広告規制に配慮する
- 公式LINEやLステップ側に不要な複雑タグを増やさない

## 3. 公式LINE・Lステップ利用時のデータ方針

### 3.1 基本方針

本サービスでは、公式LINEを小規模店舗における主要な顧客接点として扱う。一方で、Lステップは必須前提とはせず、高度なLINE配信・シナリオ運用が必要な場合に利用する任意ツールとして位置づける。

本サービスのデータ方針は以下である。

> 顧客理解・セグメント判断・施策判断・LINE配信実行・結果分析まで本サービス側で一貫して管理する。Lステップ等の外部ツールには複雑なシナリオ分岐が必要な場合のみ、最小限のタグ・対象者リスト・配信文を渡す任意連携として位置づける。

### 3.2 セグメント・タグの管理場所

| 情報 | 管理場所 | 理由 |
|---|---|---|
| 顧客状態 | 本サービス | 休眠、初回後、VIPなどの判断根拠を保持するため |
| 推定ニーズ | 本サービス | 価格不安、継続迷い、季節悩みなどを詳細管理するため |
| 行動阻害要因 | 本サービス | 予約しない理由や離脱理由を推定するため |
| 次アクション | 本サービス | 配信、個別連絡、投稿、店頭対応を横断管理するため |
| 施策目的 | 本サービス | 休眠復帰、初回後フォロー、アップセルなどを管理するため |
| LINE友だちデータ | 本サービス（Phase 5〜） | LINE友だちと既存顧客の紐付け、タグ管理 |
| LINE配信実行 | 本サービス（Phase 5〜） | 承認済み文案からBroadcast/Multicast/ステップ配信 |
| 配信結果データ | 本サービス（Phase 5〜 LINE Insights API経由） | 配信後の反応・改善提案に活用 |
| 実行用タグ | Lステップ（任意） | 複雑なシナリオ分岐が必要な場合の任意連携 |
| 配信対象者リスト | 本サービスから出力（Phase 1〜4） | Lステップ等任意ツールへの反映用（Phase 5以降は本サービスで実行） |
| 配信文・投稿文 | 本サービスで生成 | 人間承認後にLINE/各チャネルへ反映 |

### 3.3 タグ最小化の原則

公式LINEやLステップ側に恒久的なタグを大量に作ると、運用が複雑化し、属人化しやすい。そのため、本サービスでは以下の原則を採用する。

- 詳細な顧客理解は本サービス側に保持する
- 外部配信ツールには実行上必要な最小限のタグだけを渡す
- 施策ごとの一時タグを活用し、不要になったタグは整理する
- Lステップ側のタグは「状態」よりも「実行用途」に寄せる
- タグ名、作成理由、対象条件、有効期限を本サービス側に記録する

### 3.4 外部ツール側に渡すタグ例

| タグ種別 | 例 | 用途 |
|---|---|---|
| 状態タグ | 初回後フォロー対象、休眠復帰対象、VIP候補 | 配信対象の大枠指定 |
| 施策タグ | 休眠復帰_2026年05月、回数券更新_2026年06月 | 施策単位の配信管理 |
| 注意タグ | 要個別対応、配信停止、クレーム注意 | 誤配信防止・個別対応 |
| チャネルタグ | LINE配信対象、個別連絡対象 | 実行チャネルの識別 |

### 3.5 本サービス側に保持する詳細情報

| データ | 内容 |
|---|---|
| 顧客状態 | 新規、初回後、リピーター、休眠予備軍、休眠、VIPなど |
| 推定ニーズ | 価格不安、効果確認、継続迷い、季節悩み、決め手不足など |
| 行動阻害要因 | 忘れている、価格不安、予約の決め手不足、他店流出など |
| 次アクション | LINE配信、個別連絡、Instagram訴求、Google投稿、店頭提案など |
| 判断根拠 | 最終来店日、来店回数、売上、クリック、予約有無など |
| AI信頼度 | 高・中・低 |
| 施策履歴 | いつ、誰に、何を、どの媒体で実施したか |
| 結果 | 返信、予約、来店、売上、反応なしなど |

## 10. 匿名化・集計化方針

### 10.1 匿名化対象

横断分析や二次活用では、以下を直接利用しない。

- 顧客氏名
- 電話番号
- メールアドレス
- LINE userId
- 詳細住所
- 個別メモの個人特定部分
- 店舗が特定される営業秘密
- 支援者が持つ顧客固有の提案ノウハウ

### 10.2 集計単位

| 集計単位 | 利用例 |
|---|---|
| 業種別 | エステ、整体、ジムなどの平均指標 |
| 規模別 | 月商、顧客数、店舗数など |
| 地域別 | 市区町村、駅圏、商圏 |
| 顧客状態別 | 新規、休眠、VIPなど |
| 施策目的別 | 再来店、休眠復帰、アップセルなど |
| チャネル別 | 公式LINE、Instagram、Google、個別連絡など |

### 10.3 最小集計数

個別店舗や個人が推測されないよう、横断分析では一定以上の件数を持つ集計単位のみ利用する。

初期案：

- 顧客単位の集計：50件以上
- 店舗単位のベンチマーク：同カテゴリで5店舗以上
- 地域別分析：同地域または近隣カテゴリで一定件数以上
- 支援者別分析：個別代理店が特定されない形に集計

| 古い情報 | 顧客状態や連絡先が更新されていない |
| 主観メモ | スタッフメモが曖昧、感情的、ばらつきがある |
| 外部タグ肥大化 | Lステップ/LINE側に不要なタグが増える |
| データ不足 | 初期店舗では件数が少なくAI推定が不安定 |

### 11.2 対策

| 対策 | 内容 |
|---|---|
| 入力テンプレート | 業種別CSVテンプレートを用意する |
| マスタ管理 | メニュー、流入経路、施策目的を選択式にする |
| 重複検知 | 氏名、電話、メールなどで候補を提示する |
| 必須項目チェック | 分析に必要な最低項目をチェックする |
| 信頼度表示 | データ不足時はAI提案の信頼度を下げて表示する |
| 補足質問 | AIが不足データを質問する |
| タグ棚卸し | 外部ツール側の不要タグを洗い出す |

## 12. AI活用とデータの関係

### 12.1 AIが参照するデータ

AIは相談内容に応じて、必要なデータのみを参照する。

| 相談内容 | 主に参照するデータ |
|---|---|
| 売上が落ちた理由 | 売上、来店数、客単価、施策履歴 |
| 休眠客対策 | 最終来店日、来店回数、配信履歴、ニーズ |
| LINE配信相談 | 顧客状態、配信履歴、反応、配信停止状態 |
| Lステップ導入判断 | 顧客数、配信頻度、シナリオ必要性、運用体制 |
| タグ設計相談 | セグメント判定、施策目的、外部ツール状況 |
| 発信テーマ相談 | 業種、メニュー、エリア、季節、反応履歴 |
| アップセル相談 | 購買履歴、施術履歴、LTV、ニーズ |
| 新規集客相談 | 流入経路、エリア、競合、SNS/LINE反応 |
| 代理店向け提案書作成 | 店舗情報、課題、施策履歴、月次結果 |

### 12.2 AI出力に必要な根拠

AIの提案には、以下の根拠をできるだけ表示する。

- 参照した指標
- 対象人数
- 期間
- 顧客状態
- 過去施策の反応
- 外部タグ/セグメントの有無
- データ不足の有無
- 推定である場合の注意

### 12.3 AI提案の信頼度

AI出力には、必要に応じて信頼度を付与する。

| 信頼度 | 条件例 |
|---|---|
| 高 | 必要データが十分あり、過去反応も確認できる |
| 中 | 基本データはあるが、反応データが不足 |
| 低 | データが少なく、一般的な業種テンプレートに依存 |

## 13. 将来的なデータサービス構想

本システムのデータ基盤を活用し、将来的に以下のサービスを検討する。

### 13.1 業種別ベンチマーク

同業種・同規模店舗と比較して、自社の位置を可視化する。

例：

- 再来店率
- 休眠率
- 客単価
- 配信頻度
- 施策実行率
- SNS投稿頻度
- 公式LINE活用度

### 13.2 エリア需要レポート

地域ごとのニーズ、競合、季節需要を分析する。

例：

- 今増えている悩み
- 競合が打ち出しているメニュー
- エリア内の価格帯
- 季節ごとの発信テーマ

### 13.3 施策テンプレートエンジン

成功した施策パターンをテンプレート化し、他店舗にも提案可能にする。

例：

- 初回来店後フォロー文
- 休眠復帰キャンペーン
- 回数券更新案内
- Instagram投稿シリーズ
- Google投稿テンプレート
- 公式LINE配信テンプレート

### 13.4 タグ・セグメント設計テンプレート

業種別、目的別に、外部ツールへ渡す最小タグ設計をテンプレート化する。

例：

- エステ向け休眠復帰タグ設計
- 整体向け回数券更新タグ設計
- ジム向け体験後フォロータグ設計
- Lステップ構築前のタグ棚卸しテンプレート

### 13.5 休眠・離脱予測モデル

顧客の行動履歴や反応から、休眠・離脱リスクを予測する。

### 13.6 新規出店・メニュー開発支援

地域需要、競合、既存顧客ニーズをもとに、新規出店や新メニュー開発を支援する。

## 14. リスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| 個人情報リスク | 顧客情報の漏洩・過剰利用 | 最小取得、権限管理、暗号化、ログ管理 |
| 店舗不信 | 自社データが競合に使われる懸念 | 匿名化、目的明示、店舗別保護 |
| 支援者不信 | 代理店の提案ノウハウが流用される懸念 | 支援者データの分離、匿名集計ルール |
| AI誤提案 | データ不足や誤解による不適切提案 | 信頼度表示、人間承認、注意文 |
| 法規制リスク | 美容、医療類似、広告表現の問題 | 業種別禁止表現、承認フロー |
| データ偏り | 一部業種・地域に偏った提案 | 業種別テンプレート、データ量表示 |
| 過剰販促 | 顧客に不快な配信を促す | 配信頻度制御、配信停止管理 |
| 外部タグ肥大化 | Lステップ/LINE側の運用が複雑化 | タグ最小化、有効期限、棚卸し機能 |
| 成果保証誤認 | 売上向上を保証すると誤解される | 予測・提案であり保証ではない旨を明示 |
